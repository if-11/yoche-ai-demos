# 参考图视觉导演

将参考图片转化为有视觉证据支撑的导演方案和可直接用于生成的提示词。始终把风格参考图视为“如何拍”，把场景参考图视为“拍什么”。

## 核心原则

当用户要求或参考图之间发生冲突时，按照以下优先级处理：

1. 遵循用户明确提出的要求。
2. 保持场景参考图中可见的事实与结构。
3. 只从风格参考图迁移视觉语言。
4. 仅在参考图没有提供证据时使用模型默认判断。

禁止让风格迁移改变主体身份、产品结构、车型结构、方向盘位置、座椅排列、空间比例或其他事实属性。

## 读取配套规则

- 生成最终结果前，读取 [references/output-schema.md](references/output-schema.md)。
- 任意参考图中出现车辆或车辆内饰时，读取 [references/automotive-fidelity.md](references/automotive-fidelity.md)。
- 用户指定目标图像模型或要求模型专用语法时，读取 [references/model-adapters.md](references/model-adapters.md)。

## 工作流程

### 1. 核对并标记输入图片

识别且只识别一张风格参考图，并识别至少一张场景参考图。

- 优先使用用户提供的标签，例如 `Reference_A` 和 `My_Reference_01`。
- 将“参考图1的视觉风格”“图1作为风格参考”“第一张图决定怎么拍”等自然语言直接映射为 `Reference_A`，不要求用户使用技术标签。
- 将“参考图2的车型”“图2作为人物动作参考”“第三张图提供环境”等自然语言映射为对应的 `My_Reference_xx` 及其用途。
- 没有标签时，根据用户随图片提供的文字说明判断图片角色。
- 图片角色不明确时，不得仅凭上传顺序做出判断。
- 无法可靠区分风格参考图与场景参考图时，只提出一个简洁的澄清问题。
- 禁止虚构、补充或分析用户没有上传的图片。
- 只把图片附件计入参考图清单；Skill 文件、说明文档和其他非图片附件不得计入图片编号。

将风格参考图标记为 `Reference_A`。按照实际数量，将场景参考图依次标记为 `My_Reference_01`、`My_Reference_02`，以此类推。为每张场景参考图记录所有适用用途，例如车辆、内饰、产品、环境、人物动作、人物外观、材质、服装或灯光依据。一张图片可以同时承担多种参考用途。

用户已经明确说明各图用途且不存在冲突时，直接执行，不要再次要求用户改写成标准标签，也不要重复确认。

### 标准调用示例

将以下自然语言视为完整有效的调用：

```text
使用这个 Skill：
参考图1的视觉风格；
参考图2的车型、内饰布局和方向盘位置；
参考图3的人物动作；
保持真实车辆结构不变，生成相应的 JSON 和可直接复制的中英文 Prompt。
目标模型：Flux。
```

自动将其解释为：图1决定构图、镜头、光影、色彩和氛围；图2与图3决定最终画面中的真实主体与结构；Flux 决定第二部分提示词的语法适配。

### 2. 区分视觉证据与专业推断

对每项重要判断分别记录：

- `observation`：可以从图片中直接观察到的证据；
- `inference`：基于专业知识做出的解释或摄影参数估算；
- `confidence`：使用 `high`、`medium` 或 `low`。

除非元数据或用户信息能够证实，否则将焦距、镜头类型、光圈、精确灯位和象征含义视为估算。没有充分证据时使用 `not_evident`，禁止虚构象征意义或创作者意图。

### 3. 分析风格参考图

只从 `Reference_A` 提取可迁移的视觉语言：

- 构图以及主体与画框的关系；
- 摄影机位置、高度、角度、透视、取景和潜在运动感；
- 估算的镜头类型、焦距范围和景深；
- 主光、辅光、轮廓光、实景光、环境光、反射光和负补光的关系；
- 反差、曝光、高光过渡、阴影密度和时间氛围；
- 色相关系、饱和度、色温、色板和色彩对比；
- 表面呈现、纹理反应、空气感和后期质感；
- 情绪氛围与艺术指导风格。

除非场景参考图也提供了相同内容或用户明确要求，否则禁止复制风格参考图中的人物、身份、车型、产品、地点、道具、文字、标志和叙事元素。

### 4. 提取场景事实

分析每一张 `My_Reference_xx`，整合以下事实：

- 主要主体与产品身份；
- 几何结构、比例、朝向和空间关系；
- 环境、建筑、材质和表面；
- 人物动作、姿势、身体方向、手脚位置、视线方向和表情状态；
- 适用时的车辆外观或内饰事实。

不得推断人物年龄、身份、职业、性格、族裔或个人经历。只有当用户明确需要保持人物外观，且场景参考图提供了相关依据时，才描述人物外观。

如果场景参考图互相冲突，优先采用用户明确指定负责该属性的参考图。用户没有指定时，指出冲突并请求澄清，禁止暗中合并不兼容的事实。

### 5. 制定视觉迁移方案

将风格属性映射到场景事实，不得引入没有依据的内容。明确记录：

- 从 `Reference_A` 迁移哪些视觉属性；
- 从每张 `My_Reference_xx` 锁定哪些事实；
- 哪些信息仍不确定；
- 必须防止哪些生成错误。

将锁定事实转化为正向保持指令，并将可能发生的错误转化为针对当前场景的负向限制。优先使用 `incorrect steering wheel position`、`wrong vehicle interior layout`、`changed seat arrangement`、`incorrect camera perspective` 等精确表述。除非用户明确要求，否则不要使用 `bad quality` 等泛化填充词。

### 6. 构建图像生成提示词

按照以下内部顺序分别编写中文和英文主提示词：

1. `[Scene Subject]` 场景主体
2. `[Reference Style]` 参考风格
3. `[Camera Setup]` 摄影机设置
4. `[Lighting]` 光影
5. `[Color]` 色彩
6. `[Material]` 材质
7. `[Fidelity Constraints]` 保真限制
8. `[Realism and Finish]` 真实感与成片质感

使用具体、可执行的摄影语言。不得宣称仅凭提示词就能保证主体身份或几何结构绝对一致。目标系统支持图片条件控制时，明确要求其使用上传的场景参考图保持结构一致性。

用户指定模型时，只应用该模型对应的适配规则。用户没有指定模型时，生成模型中立的主提示词，并将 `targetModel` 设置为 `generic`。

### 7. 输出前验证

逐项确认：

- 每张已上传图片都在参考图清单中出现且只出现一次；
- 每张场景参考图至少具有一个用途；
- 风格迁移没有引入缺乏依据的主体或物体；
- 没有把观察事实与参数估算混为一谈；
- 所有关键场景结构都进入了保持限制；
- 出现车辆时已经完整应用汽车专项规则；
- 中英文提示词描述的是同一个镜头；
- 负向限制均针对当前场景可能出现的具体错误；
- JSON 中的可复制提示词与第二部分展示的提示词逐字一致；
- 最终结果严格符合双交付输出规范。

## 输出行为

必要输入缺失或图片角色存在歧义时，只询问缺失信息，不得虚构完整分析。

输入充分时，严格按照 [references/output-schema.md](references/output-schema.md) 输出两个部分：

1. `PART 1 — 视觉分析 JSON`：输出完整、有效的结构化 JSON。
2. `PART 2 — 可直接复制的生成 Prompt`：分别输出中文 Prompt、英文 Prompt、适用时的 Negative Prompt 和模型参数。

第二部分必须使用独立代码块，方便用户直接复制。第二部分的提示词不得包含解释、分析过程、JSON 转义符或额外说明，并且必须与 JSON 中 `copyReadyPrompt` 的内容逐字一致。
